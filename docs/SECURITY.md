# Security model

The intended principal is one Windows owner connecting a client they trust. YGPT Local executes with that user's Windows permissions. Sanitized environment variables and path checks are **not an OS sandbox** and do not undo arbitrary subprocess effects.

Local MCP and Agent dispatch preserves this boundary. Configuration discovery does not start services or rewrite other Agents. Service connections are separate per chat/source; disabled sources remain disabled. Discovered schemas, descriptions, prompts and resource contents are untrusted data. Source credential values are excluded from the capability catalog and forwarded only to the configured service, without HTTP redirects. Tool invocations validate the exact schema and require initial tool discovery; identified destructive tools/launches use existing human review. This chat's Full Access is not forwarded to delegated Agents. Agent payloads, stdin and logs use CurrentUser DPAPI; the private task index stores ownership and a request digest. Temporary scratch is outside the protected approval/credential state tree. Uncertain effects never trigger automatic replay. See [local tools](LOCAL_TOOLS.md).

The HTTP server listens only on loopback. A public Cloudflare hostname must use HTTPS and owner-bound OAuth authorization code flow with PKCE S256, exact redirect allowlisting, one-use expiring codes and revocable, scoped access tokens. An explicit owner pairing confirmation is required. Tokens are not accepted from URL query strings. Secrets are DPAPI-encrypted at rest; diagnostics must never contain them. The owner pairing key belongs only in the OAuth confirmation page, never in a model message.

Secure MCP Tunnel is an optional private transport, subject to Platform/workspace permissions. Its runtime credential and the local MCP transport key are distinct from the operator health key. Existing production tunnels must not be reused by two runtimes.

High-risk operations pause for a one-request App capability. The private decision capability is carried only in App metadata. The model must not call decision tools. Decision replay reads existing status; it does not run the action again. Unknown effects remain unknown and must be reconciled before retrying.

Since 1.0.8, the owner can explicitly enable Full Access on a dedicated card for one server-issued chat context (default two hours, maximum twelve). This bypasses policy reviews for that context while retaining schema, path integrity, task output tokens and resource ownership. Other contexts keep their rules. Enabling does not execute pending requests; revocation affects subsequent checks, not already-running processes. The grant is persisted against the owner and context with fixed expiry; context closure also revokes it. No caller-provided mode flag or host metadata can create a grant. See [chat access](CHAT_ACCESS.md).

Since 1.0.10, the dedicated Full Access request directly renders its confirmation in the chat. Desktop binding or input requests a separate, explicit ten-minute Full Access card for the same context. Only after the person approves and the exact target binding is checked does that desktop request enable the grant and execute its original step once. It never drains or replays other pending operations. Expiry or revoke restores review before later input. Screenshot PNGs are deleted after being encoded for the inline response; local result history excludes image bytes. Old generated captures may be removed, but arbitrary user images and private recovery state are not cache.

The manual Windows approval center uses the existing owner-only named pipe, authenticated with the DPAPI-protected local control key. It lists saved requests and binds a choice to an exact request nonce and argument digest. It creates no public approval endpoint and performs no automatic decision. Widget and Windows decisions share the same durable ledger and once-only execution claim. Cross-device continuation messages are reserved and acknowledged durably; uncertain delivery is retried only through an explicit Resume chat action, never by replaying the approved operation. Missing UI or metadata grants no permission.

Snapshots cover actual listed preimages, with size/depth limits. Restore conflicts preserve newer content. Batch operations are not atomic. Old user state, credentials, databases and approval capabilities are not part of the public source tree or the release payload.

Before publication: review source and clean Git history, runtime hashes and notices, install/uninstall boundaries, OAuth negative tests, the built archive, and actual host evidence. The included automated scanner is a scoped aid, not a claim of exhaustive security audit or legal review.

Do not open public issues containing tokens, keys, cookies, private file content or raw state. Describe the issue without secrets first; arrange a private disclosure channel with the repository maintainer before sharing sensitive details.

1.0.17 changes the default pending-request lifetime to six hours, without modifying recorded grants or reviving expired requests. The Chrome DevTools adapter accepts only five fixed extension tool names with bounded string arguments and never forwards arbitrary upstream tool calls. Npm audit covers the lockfile; it does not inventory vendored code. The upstream bundle declares Zod 4.6.5 (including an oversized-collection advisory); the exposed extension schemas contain no collections and the YGPT RPC ingress is capped at 128 KiB. This bounded adapter is the applicability limit, not a claim that every vendored upstream advisory has been patched. Direct Zod is 4.6.7.
