# YGPT Local — security audit note

Scope: candidate 1.0.0-rc.13. Production stays 1.0.0-rc.2 until the owner switches it. This note states what the build does and does not guarantee. The rc.13 revision records the owner's explicit directive (2026-10-22, after a capability test of rc.9) that supersedes two rc.4-era rules: the Desktop Agent boundary is removed, and the browser gains a take-over mode next to the isolated browser. Everything is now one owner blacklist model: default allow, human gates on risk signals, no hard-denied targets.

## What is guaranteed by construction

- **Chat-only ownership.** Every tab, UIA binding, process session and durable job is owned by the server-issued chat context that created it. Another chat presenting the same ID gets `SESSION_FOREIGN`; output tokens are additionally scoped per operation. `y_close_context` revokes the context, closes its browser context and releases its UIA bindings.
- **No Desktop Agent boundary (rc.13, owner directive).** Agent/Codex processes, windows, folders and browser state are ordinary targets under the same blacklist rules as everything else: reads and clean operations are allowed by default; destructive or system signals become human gates. UIA lists every window with its real title and identity; the ChatGPT app window binds like any other once a human approves that exact window. (The rc.4–rc.12 `TARGET_FOREIGN` refusal set was removed by the owner because the capability test showed it made the tools useless in ordinary situations.)
- **UIA human approval.** `y_desktop_windows` metadata is automatic; `bind` and every input/focus `action` require a human decision from the trusted approval surface. Approvals bind to the exact window identity (exe path + SHA-256 + pid + birth + hwnd) and are re-checked before execution; a changed target refuses. Model calls, MCP parameters and `clientInfo` never count as consent.
- **Owner blacklist permission model (rc.5, completed in rc.13).** The shipped configuration is default-allow (`autonomous` + `blacklistDefaultAllow`): reads are automatic, clean writes on any volume are automatic (the engines accept absolute paths anywhere; authorization lives in the policy layer, not in a path jail), and every restriction is expressed as a human gate — system and credential-adjacent targets, batch/directory/system deletes, destructive command shapes, developer tasks outside the owner-trusted set, writes into YGPT's own runtime/state or the G: vault, protected job/download targets, and unclassified tools. **There are no hard-denied targets left in the policy layer**; the remaining `deny` outcomes are malformed-request errors (bad argv, missing paths, unknown structured task names, non-absolute paths). Deletes are snapshot-first: a single ordinary file deletes by default only because a verified protected snapshot (the rollback handle) is taken before anything is removed; if the snapshot fails, nothing is deleted.
- **Browser modes (rc.13, group discipline rc.14).** Two modes behind the same `y_browser_*` tools. The isolated browser (default) is YGPT's own Playwright instance — Chrome by default, Edge when the owner configures it — with a private context per chat, and it browses the public web: destinations follow an owner blacklist (blocklisted hosts, URLs with embedded credentials), not an enrollment list. The take-over mode (`y_browser_attach`) connects over CDP to the owner's own existing Chrome/Edge, enabled by the owner starting that browser with a remote-debugging port; detaching never closes their browser. In take-over mode YGPT works ONLY in its own tab group: tabs are created in the background (the owner's current tab stays active and their window is never focused), stamped with a `ygpt:` window marker so the group is found again and adopted on a later attach; the owner's own tabs are counted, never read, moved or closed. When several browsers/profiles are discoverable (debug ports, `DevToolsActivePort` files, profile account labels from the browser's Local State), attach returns the candidates and waits for the owner's designation — it never guesses between accounts. Platform limit (from the owner's capability test): since Chrome 136 the debug port is ignored for the default profile folder, so take-over reaches a dedicated debugging instance, not the daily profile in place; that would need the browser-extension route, which is not built in. When the choice matters the chat asks the owner for a preference and defaults to the isolated browser.
- **App-control consent inside desktop operations (rc.13).** There is no separate app enrollment product surface: the `y_desktop_bind` approval names the exact application + window (the app-control authorization), and every input/focus action asks again. Terminals, credential UI and password managers are no longer refused by the helper or the engine; they follow the same bind + per-action approvals.
- **Write safety.** Same-file writes from different chats serialize on short per-file locks with `expectedSha256` preimage checks (`STALE_PREIMAGE` on conflict, never a blind overwrite); every engine write takes a durable pre-write snapshot first. `unknown` outcomes are never replayed — recovery is read-only (`y_call_status`, `y_job_status`, `y_resource_owner`).
- **One canonical API.** The legacy compat child process and the `y_local_*` / `yuki_*` / unprefixed surfaces are deleted. Retired names execute nothing and answer `NO_TOOL` with the replacement, so a stale cached chat fails loudly instead of silently driving a second API.
- **Provenance honesty.** Call records carry the server-issued context label and the transport kind. Where the host does not attest its type, `y_usage_report` and `y_recent_calls` say `unverified`; nothing in the codebase guesses "Chat vs Agent" from model-supplied data.

## What is NOT guaranteed (read before switching production)

- **No OS sandbox for arbitrary code.** A job or process the owner approves runs as the current Windows user and can reach anything that user can reach. This is stated in `y_policy` (`noOsSandbox: true`) and in the approval cards; it is not fixable by pattern scanning. The high-risk signal scan + human gate is a review aid, not a proof of safety.
- **Host identity is not attested.** The platform does not prove whether a caller is an ordinary chat or the Desktop Agent. Since rc.13 there is deliberately no target-side distinction either (owner directive); what remains is per-chat resource ownership (a chat only operates what it created) and the human gates.
- **File races with external editors.** `expectedSha256` + snapshot + re-check-before-commit narrows the race to the final commit window; a process that rewrites a file in that exact window can still interleave. Conflicts surface as errors, not silent corruption of YGPT's own writes.
- **Command rollback is bounded.** Typed file operations are fully snapshot-covered; arbitrary commands and jobs get a bounded pre-run snapshot of the working directory (file count/size/extension limits, stated in the result as `prewriteBackup.coverage`). A command that deletes files outside that bounded set is not guaranteed recoverable — the Recycle Bin and the high-risk command gate are the mitigations, and this limit is deliberate and documented rather than hidden.
- **Recycle Bin restore limits.** `y_file_trash` keeps a protected snapshot (restore via `y_backup_restore`) and records a trash manifest, but the Windows Recycle Bin copy itself follows normal Windows behaviour (size quotas can purge it). The snapshot is the reliable restore path.
- **Linux verification limits.** This candidate was assembled and checked on Linux: C# compiles via Roslyn (including `NativeWindows.exe`, built against the official PowerShell 5.1 reference assemblies), portable Node tests, CSP and the public audit pass. UIA against real Windows applications, the installer lifecycle and ChatGPT host behaviour are **not** proven by those checks — they are the owner's on-device acceptance tests (see `docs/UPGRADE_TEST_RESULTS.md`).

## Evidence for the rc.13 model

- `tests/blacklist-rc13.test.mjs`: the access policy returns no hard refusal for Agent targets, YGPT state, the vault, protected job/download targets, unclassified tools or untrusted developer tasks — each is `allow` or `approve`; the only `deny` left is a malformed request (unknown structured task name).
- `tests/upgrade-portable.test.mjs`: window classification never protects (Agent process/tree/signer/unverifiable all list openly), the browser destination blacklist (blocklist, embedded credentials, legacy localhost migration, opt-in allowlist), any window — including the ChatGPT app and a password manager — binds after broker approval, and UIA targets stay owned by the binding chat (`SESSION_FOREIGN` for others).
- `runtime/ownership.mjs` + `runtime/durable.mjs`: context-scoped resource rows, foreign counts, token scoping; unit-covered.
- Browser: per-chat isolated contexts with idle sweep and `BROWSER_CONTEXT_CLOSED` semantics; take-over tabs are owned by the attaching chat and disconnect without closing the owner's browser.
